# Legal Launch Audit

Decide what **this** project legally needs before launch: no more, no less. Then prove each finding with `file:line` evidence and an official source.

> Not legal advice. The output is a structured pre-check for the team and their lawyer. Never present it as a final legal opinion.

## Ground rules

1. **Read-only by default.** Do not edit code, configs or legal texts until the user approves the fix list.
2. **Evidence or it did not happen.** Every code claim cites `path:line`. Every "missing" claim says what was searched.
3. **Context decides.** A page is not required just because a generic checklist lists it. Use [references/matrix.md](references/matrix.md) to mark each item as required, conditional, unnecessary or to-avoid for this project type and market.
4. **Code cannot prove registrations or contracts.** Items like ETBİS, VERBİS, İYS, KVKK standard contracts, DPAs and store console settings get ❓ and a precise question, unless the user confirms them.
5. **Do not invent law.** Use the reference files, which carry a "Last verified" date. If something may have changed since then, or the user's market is not covered, say so and check the official source (search the web if a tool is available).
6. **No attribution in user files.** Never add "generated by" lines, tool names or signatures to files you create or edit in the user's project.
7. **Language.** Answer in the user's language. Keep legal terms in their original language where useful (e.g. *aydınlatma metni*, *cayma hakkı*, *Impressum*).

## Workflow

### 1. Scan

Run the detector from this skill's folder against the project root:

```bash
python3 scripts/detect.py <project-root> --format md
```

It lists:
- trackers, ad SDKs, consent managers, accounts and payments,
- foreign processors, permissions, AI features and user-generated content,
- legal pages, with `file:line` evidence and suggested review flags.

It is heuristic, so open the cited files to confirm before you report. If Python is unavailable, search the code manually for the same signals (see the categories in the script).

### 2. Understand what the product does

Legal needs follow from **purpose and features**, not from the tech stack. Before judging anything:

1. Read the detector's "What the project seems to be" and "Sector hints" sections. Then open the sources it points to: README, store listing text (fastlane/metadata), package/pubspec descriptions, app name, the main screens/routes and the onboarding flow.
2. Write a **one-paragraph product summary** covering:
   - what the product does and for whom (consumers/businesses, age group),
   - how it makes money (sales, subscription, ads, free),
   - which personal data it needs and why,
   - which features carry legal weight (accounts, payments, social/chat, location, health, AI, user content).
3. Match it to sectors in [references/sectors.md](references/sectors.md). Sector rules often matter more than generic pages: health data, finance licences, kids, gambling, social features.
4. Show the summary to the user and ask them to correct it. A wrong purpose means wrong advice. If the user is not available, mark it as an assumption.

### 3. Build the project profile

Fill these from the scan and the summary, then ask the user **only** for what the code cannot answer, in one short message:

| Question | Why it matters |
|---|---|
| Target markets (TR, EU/which country, US, global)? | Selects reference files |
| Selling to consumers (B2C) or only businesses (B2B)? | Distance-sales and withdrawal rules are B2C |
| Legal entity type and country (company, sole trader, individual)? | Imprint, trader status, VERBİS |
| Paid features and how (own checkout, App Store/Play billing)? | Who is the seller, subscription rules |
| Marketing SMS/email? | İYS, consent |
| Children among users? Health or other sensitive data? | COPPA, special-category data |
| Employee count and size (for TR VERBİS, EU accessibility microenterprise test)? | Exemptions |

If the user is not available, choose the most reasonable reading, write the assumptions at the top of the report, and continue.

Map the project to one or more **project types (A–G)** from the matrix.

### 4. Load only the references you need

- Always: [references/matrix.md](references/matrix.md) and [references/report-format.md](references/report-format.md)
- Türkiye users or Turkish market: [references/turkiye.md](references/turkiye.md)
- EU/EEA/UK users: [references/eu.md](references/eu.md)
- US users: [references/us.md](references/us.md)
- iOS or Android app: [references/app-stores.md](references/app-stores.md)
- The product falls into a sector (health, finance, kids, social, gambling, AI, IoT…): [references/sectors.md](references/sectors.md)

### 5. Evaluate

For every matrix row that applies to the project types:

1. Decide **R / C / O / – / X** for this project (resolve each C using the profile).
2. Check the code and pages: ✅ present and consistent, ❌ missing, ⚠️ present but wrong, ➖ not applicable (with reason), ❓ needs a human fact, 🗑️ unnecessary clutter.
3. Run these **consistency checks**. They catch most real problems:
   - Every SDK and processor found is named in the privacy notice. For mobile, it must also appear in the store labels (Apple App Privacy / Google Data safety).
   - No analytics/ad/pixel code runs before consent (look at `<head>` tags, SDK init in `main`/`App`/`Application.onCreate`).
   - The consent UI has an equal "reject" option, no pre-ticked boxes, and no "by continuing you accept".
   - Explicit-consent (*açık rıza*) checkboxes are not forced on forms that do not need consent.
   - The notice is linked at every collection point (forms, sign-up, checkout, app first run).
   - Sign-up exists → in-app account deletion exists. For Google Play there must also be a web deletion page.
   - Prices shown include taxes and mandatory fees, and discount reference prices follow the TR 10-day / EU 30-day rule.
   - Permissions declared in the manifest/plist are used and explained.
   - Outdated items (EU ODR link, old cookie law wording) are flagged 🗑️.
4. Assign **P0–P3** using report-format.md.

**How to write each finding** (this is what makes the report useful):
- **Tie it to the product.** Name the feature and screen that triggers the rule, e.g. "Your app lets users follow each other (`lib/social/follow.dart:20`), so in Türkiye it counts as a social network provider…". Never write a finding that would be identical for any other project.
- **Explain in plain language** for a founder who is not a lawyer: what the rule requires, why it applies here, and what happens if ignored (store rejection, fine, complaint), in 1–3 sentences.
- **Give a concrete fix:** where in the code/UI, what to add or remove, and which template or SDK helps. Include a short code example when it removes ambiguity.
- **Say what is not needed** and why, so the user does not add clutter.
- **Be honest about uncertainty:** facts you assumed, rules whose scope is unclear, and anything that needs a lawyer, accountant or licence check.

### 6. Report

Follow [references/report-format.md](references/report-format.md) exactly:
- product summary and profile,
- findings table with evidence and sources,
- "not needed / remove" list,
- "needs a human decision" questions,
- prioritised action plan,
- limits.

Show the report in chat. Write it to a file (e.g. `docs/LEGAL_AUDIT.md`) only if the user asks.

### 7. Fix mode (only after approval)

When the user approves specific items:
- Code fixes:
  - gate trackers behind consent,
  - add the account-deletion flow,
  - remove pre-ticked boxes,
  - add footer links,
  - remove unused permissions.
- Legal texts: draft from the repository's `templates/` folder if available, fill in only facts found in the code or given by the user, and leave clear placeholders for everything else. Mark drafts as requiring legal review.
- After changes, re-run the detector and show what changed.

## Out of scope: always say so

Tax registration and invoicing, company formation, trademark clearance, sector licences (health, finance, gambling, alcohol…), employment law, and contract negotiation. Recommend a lawyer or accountant for these, and for final review of every legal text.
